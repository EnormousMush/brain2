## 1. 一句话定位

**他山 / Whetstone 把一个人的知识按领域拆成多个"副脑",每个副脑由一个 agent 代理,让它们在一个受控环境里长时间互相提问、互相反驳,替用户想到他自己想不到的东西。**

对比记忆:
- Obsidian:帮你**存**,不帮你**想**
- Notion AI / NotebookLM:你问它才答,单一知识库,单一人格
- ChatGPT Memory:单一人格,无结构,不会自我碰撞

我们是唯一一个**主动的、多人格的、跨库的**思考工具。别人解决"我写过的东西在哪",我们解决"我没想到的东西是什么"。

## 2. 术语表(三位 agent 必须统一用词)

| 术语 | 英文 / 代码标识 | 定义 |
|---|---|---|
| 副脑 | `Brain` | 一个可检索的知识单元。可以是一个领域(音乐、数学)、一个项目、一本书的读书笔记。物理形态是一个目录 |
| 副脑名片 | `BrainCard` | 副脑的 300 至 800 token 自我摘要,是副脑对外的"身份证"。跨副脑通信只传名片,不传原文 |
| 副脑 Agent | `BrainAgent` | 代理某个副脑发言的 agent,由 `persona + BrainCard + 模型配置` 定义 |
| 圆桌 | `Roundtable` | 一次有明确议题、有起止条件、有预算上限的辩论会话 |
| 黑板 | `Blackboard` | 圆桌的共享工作区,含发言流水 + 当前共识/分歧/开放问题 |
| Eureka | `Spark` | 用户瞬时记录的原始碎片,是圆桌的种子 |
| 新连接 | `EdgeProposal` | 辩论中新生成的跨副脑关联,是我们最核心的产出物 |
| 洞察账本 | `InsightLedger` | 结构化沉淀所有 EdgeProposal / 痛点 / 行动项的表,带完整溯源 |
| 主持人 | `Moderator` | 负责拆解议题、控场、判定收敛的特殊 agent |
| 收割者 | `Harvester` | 每 N 轮从黑板提炼结构化洞察并压缩历史的特殊 agent |

## 3. 核心洞察:为什么是这个,为什么是现在

**痛点的准确表述**(v0.1 说的"帮用户找到隐藏很深的痛点"太模糊,建议改成下面这句):

> 一个跨领域的人,知识是分区存放的。音乐的直觉不会自动去敲数学的门,读过的论文不会自动跑来解决手上的项目。人脑做跨领域联想的效率极低,而且高度依赖偶然。现有工具全部是被动检索,只会在你已经知道要找什么的时候才有用。

**为什么现在能做**:
1. 长上下文 + 工具调用成熟,agent 之间可以"互相提问"而不是"互相塞资料"
2. 小模型足够便宜,可以支撑几十轮的自动对话
3. 多厂商模型可以混编,不同模型的先验差异本身就是创造力来源(这一点是我们的独特赌注)

**我们的反直觉主张**:创造力不来自更强的单个模型,而来自**被强制对话的、有差异的、有各自私有知识的多个主体**。

## 4. 系统架构

### 4.1 分层

```
┌──────────────────────────────────────────────┐
│  交互层 (Agent C)                             │
│  Eureka 输入 · 辩论实时流 · 3D 知识群 · 洞察卡片 │
└───────────────┬──────────────────────────────┘
                │ REST + SSE
┌───────────────▼──────────────────────────────┐
│  辩论层 (Agent B)                             │
│  Moderator · Scheduler · Blackboard           │
│  Harvester · CostGuard · ModelGateway         │
└───────────────┬──────────────────────────────┘
                │ ask_brain(brain_id, question)
┌───────────────▼──────────────────────────────┐
│  副脑层 (Agent A)                             │
│  Ingest · Chunk · Embed · BrainCard · Retrieve │
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│  存储:文件系统(副脑) + SQLite(账本)        │
└──────────────────────────────────────────────┘
```

存储刻意用**纯文件 + SQLite**,不上向量数据库。理由:副脑规模在万级 chunk 以内,numpy 余弦足够;本地优先的存储形态直接服务于我们的隐私叙事和开源叙事。

### 4.2 数据模型

**副脑目录结构**

```
brains/
  music/
    brain.yaml          # 元信息
    sources/            # 原始导入文件(只读)
    notes/*.md          # 原子笔记,带 frontmatter
    index.npz           # embeddings 矩阵 + chunk 映射
    card.md             # BrainCard,自动生成,可人工微调
```

**brain.yaml**

```yaml
id: music
name: 音乐脑
domain: 音乐制作与和声理论
persona: |
  你从声音的质感、张力和时间感出发思考问题。
  你厌恶抽象概念,凡事都要问"它听起来是什么样"。
model:
  provider: anthropic        # anthropic | openai | google | deepseek | qwen
  name: claude-sonnet-4-6
  temperature: 0.9
retrieval:
  top_k: 5
  max_chunk_tokens: 200
stats:
  note_count: 128
  last_indexed: [phone]T09:00:00Z
```

**note frontmatter**

```yaml
---
id: mus-0042
title: 属七和弦的悬置张力
source: sources/harmony-notes.md#L120-L160
created: [phone]
tags: [和声, 张力]
---
```

`source` 字段是**溯源的命根子**,ingest 阶段必须写入,否则可视化和洞察卡片都点不回原文。

## 5. 模块一:Eureka(瞬时记录)

### 5.1 设计原则

**零摩擦优先于结构化。** 用户在灵感闪现的两秒内不会做分类。因此:
- 只有一个输入框,一个快捷键
- 不让用户选副脑,不让用户打标签
- 输入即存,分类是后台的事

### 5.2 支持的输入形态

| 形态 | 优先级 | 说明 |
|---|---|---|
| 文字 | MUST | 一句话、一个词都行 |
| 语音 | SHOULD | Whisper 或系统语音转写,demo 现场说一句话很有戏剧性 |
| URL | COULD | 抓取正文,当作"我觉得有趣的已有产品" |
| 图片/截图 | WON'T | 本次不做 |

### 5.3 后台 pipeline

```
原始输入
  → 归一化(转写 / 抓正文)
  → embedding
  → 软路由:与各 BrainCard embedding 算相似度,取 top-2 作为"归属副脑"(允许多归属)
  → LLM 生成 3 个"为什么这可能有趣"的钩子(每个 ≤ 30 字)
  → 落库为 Spark
```

**钩子(hooks)是关键的产品设计。** 它把一条死掉的碎片变成三个可以开圆桌的议题,让用户看到"我这句废话原来有三个方向"。

### 5.4 Spark 到圆桌

每条 Spark 卡片上有一个按钮:**召开圆桌**。点击后系统自动:
1. 用 Spark 的 embedding 匹配最相关的 3 至 4 个副脑
2. 允许用户手动增删参会副脑(这一步不能省,用户需要掌控感,也是 demo 的互动点)
3. 设定预算滑块(轮数 / 花费上限)
4. 开跑

## 6. 模块二:副脑辩论环境(技术核心)

### 6.1 关键架构决策:ask-tool,不是 context 拼接

**朴素做法**:把每个副脑的知识检索出来,拼进一个大 prompt,让模型扮演多个角色。
**问题**:context 随副脑数和轮数爆炸,成本失控,而且角色会串味,失去差异性。

**我们的做法**:每个副脑 agent 只装载**自己**的知识,别的副脑对它而言只是一个**可调用的工具**。

```
BrainAgent(music) 的 context =
    persona(音乐脑)                          ~150 tok
  + 自己的 BrainCard                          ~500 tok
  + 其他副脑的一行摘要 × N                    ~80 tok × N
  + 黑板当前状态(共识/分歧/开放问题)        ~400 tok
  + 最近 K=6 条发言                           ~1200 tok
  + 本轮自己 ask_brain 检索到的片段           ~800 tok
  ─────────────────────────────────────────
  总计约 3.5k tok,与轮数无关,与副脑总规模无关
```

它可以调用 `ask_brain("math", "你那边有没有关于收敛性的说法")`,检索在数学脑内部发生,回来的只有精炼答案。**这是我们回答"如何长时间交流同时保护 context window"的核心答案。**

### 6.2 黑板与调度

**黑板结构**

```json
{
  "topic": "...",
  "round": 7,
  "consensus": ["两边都认为张力来自未解决的期待"],
  "tensions": ["音乐脑认为张力是时间性的,数学脑认为是结构性的"],
  "open_questions": ["能否给'期待'一个可计算的定义"],
  "recent_turns": [...],
  "compacted_history": "前 6 轮摘要,≤300字"
}
```

`consensus / tensions / open_questions` 每轮由 Moderator 增量更新,是整个系统的"工作记忆"。

**调度器(不要用简单轮询)**

发言权按分数选取:

```
score(brain) = 0.6 × sim(brain_card, 当前最热 open_question)
             + 0.2 × 随机扰动
             - 0.2 × 最近发言次数惩罚
```

理由:轮询会让不相关的副脑说废话烧钱;纯相关性会让一个副脑霸麦。惩罚项保证多样性,随机扰动保证不同次运行结果不同(demo 时这是优点,可以现场跑两次给出不同结果)。

**轮次结构**

```
Round 0    Moderator 把 Spark 拆成 3 至 5 个 open_questions
Round 1-N  每轮选 2 个副脑发言,每次发言硬上限 200 token
每 3 轮    Harvester 提炼 InsightRecord,压缩历史,重算 novelty
终止       达到早停条件或预算耗尽(见 6.4)
最后一轮   Moderator 输出总结 + 排序后的洞察列表
```

**发言强制格式**(防止 agent 互相吹捧,这是多 agent 系统最常见的失败模式):

每次发言必须从以下四选一开头,并写在结构化字段里:
- `质疑:` 指出上一位发言的问题
- `连接:` 把对方的概念映射到自己领域的某个东西
- `追问:` 提出一个对方必须回答的具体问题
- `提议:` 给出一个可执行的行动

**禁止**纯附和。Moderator 检测到连续两轮无 `质疑` 或 `追问` 时,强制注入一个 devil's advocate 提示。

### 6.3 异构厂商混编

不同副脑挂不同厂商的模型,这是 v0.1 里"通过不同公司 agent 的交流拿到意想不到的结果"的落地方式。

实现上极其廉价:统一走一个 OpenAI 兼容网关,`brain.yaml` 里一个 `provider` 字段决定路由。

```
音乐脑  → Claude      (语言细腻,擅长质感描述)
数学脑  → GPT / o 系列 (形式化推理)
影像脑  → Gemini      (多模态先验)
金融脑  → DeepSeek    (成本低,可高频发言)
```

Demo 时这一点要**明说**:界面上每个副脑头像旁边标注厂商 logo。评委会记住这个细节。

### 6.4 成本控制与早停

**分层用模型**
- 常规发言:小模型(Haiku / Flash / DeepSeek)
- Moderator 与 Harvester:大模型
- 最终总结:大模型

**Prompt caching**:persona + BrainCard + 其他副脑摘要 是每轮不变的前缀,必须命中缓存。

**早停条件**(满足任一即停):
1. **新颖度衰减**:连续 3 轮 Harvester 产出的 InsightRecord 与账本中已有条目的最大余弦相似度 > 0.85
2. **开放问题清空**:`open_questions` 为空且无新问题产生
3. **预算耗尽**:轮数或美元花费触顶
4. **死循环检测**:最近 4 轮发言两两相似度均 > 0.9

**预算作为一等公民**:UI 上直接让用户选"花 5 毛钱聊一下"或"花 5 块钱深聊",实时显示已花费。这既是工程约束,也是可以讲给评委听的产品洞察。

### 6.5 产出物

辩论的产出**绝不能是一段聊天记录**。必须是结构化的 InsightRecord 列表,按 `novelty × confidence` 排序,每条可点击展开到原文。

三种类型:
- `edge` 新连接:A 领域的概念 X 与 B 领域的概念 Y 的对应关系
- `pain_point` 痛点:你在 A 里反复抱怨的事,B 里有现成解法
- `action` 行动项:今天就能做的下一步

## 7. 模块三:知识群可视化

### 7.1 为什么 Obsidian 的 3D 图不够用

Obsidian 的图谱只画**用户手动写的 wiki-link 拓扑**。结果是:好看,但信息量为零,没人真的靠它做决策。用户看完的反应是"哇"然后关掉。

### 7.2 我们的三个差异化

**差异化一:语义布局,不是拓扑布局**
节点位置由 embedding 降维(UMAP / t-SNE)决定,语义相近的东西**在空间上就是近的**。用户可以"看出"知识分布,而不只是看到一团毛线。

**差异化二:三类边,视觉上必须分得开**

| 边类型 | 来源 | 视觉 |
|---|---|---|
| `explicit` | 用户手写的链接 | 灰色细线,静态 |
| `semantic` | 系统算的相似度 | 淡蓝虚线,半透明 |
| `discovered` | **辩论新生成的连接** | 高亮实线,发光,有生长动画 |

`discovered` 是我们的爆点。用户跑完一场辩论,回到图上,看到几条从没存在过的线**正在长出来**,连接了他从没想过会有关系的两个星团。

**差异化三:时间轴 scrub**
拖动时间轴,重放整场辩论:第 3 轮长出这条边,第 7 轮长出那条。这是 demo 的高光时刻,也是"可评估性"的实现:用户能看到一个想法是**怎么**被想出来的,而不只是结果。

### 7.3 图数据契约

```json
{
  "nodes": [
    {"id":"music","type":"brain","label":"音乐脑","x":..,"y":..,"z":..,"size":128,"color":"#..."},
    {"id":"mus-0042","type":"note","parent":"music","label":"属七和弦的悬置张力","x":..}
  ],
  "edges": [
    {"source":"mus-0042","target":"mth-0117","type":"discovered",
     "insight_id":"ins-007","novelty":0.71,"created_round":4}
  ]
}
```

### 7.4 交互层级

- **默认视图**:只显示副脑级节点(星团),避免上来就是一万个点的视觉噪音
- **点击副脑**:展开该副脑内部 note 节点
- **点击 discovered 边**:弹出对应的 InsightRecord 卡片,含双向溯源链接
- **反馈**:每条 discovered 边可以点赞或点踩。点赞的边转为永久 `explicit` 边,写回知识库

最后这条是产品闭环:**用户的点赞点踩就是我们的数据护城河**,它训练的是"对这个用户而言什么算好想法"。

### 7.5 技术选型

`react-force-graph-3d`(three.js 封装)可以在半天内跑起来,自带力导向布局和节点点击。不要从零写 three.js 场景。团队已有 Three.js 3D 交互可视化的实战经验,这块是我们的相对优势,应该把时间花在**边的动画和时间轴**上,而不是花在搭基础场景上。

## 8. 副脑冷启动(v0.1 难点一的答案)

分四层,难度和数据量递增。**本次只做 L0 和 L1。**

| 层 | 方式 | 耗时 | 本次 |
|---|---|---|---|
| **L0** | 引导式问卷 / 5 分钟语音自述 → LLM 生成 3 个种子副脑,每个约 10 条 note | 5 分钟 | MUST |
| **L1** | 拖入一个文件夹(md / txt / pdf)→ 自动切分、聚类、命名副脑 | 2 分钟 | MUST |
| L2 | Obsidian vault(本质就是文件夹)、Notion 导出、Readwise、微信读书 | 10 分钟 | SHOULD(Obsidian 免费送) |
| L3 | Google Drive / Gmail / 浏览器历史,持续同步 | 持续 | WON'T |

**L0 的问卷设计**(这是"完全不记笔记的人"的解法,也是我们最需要打磨的产品细节):

不要问"你的知识领域有哪些"。用户答不上来。要问具体的行为问题:
- 最近三个月你反复在想的一件事是什么
- 你会为了什么东西熬夜
- 别人经常来问你什么
- 你最近一次觉得"这个我早该知道"是什么时候

四个问题的答案交给 LLM,直接生成 3 个带 persona 的种子副脑。**这一段本身就是很好的 demo 素材**:五分钟从零到有三个副脑开始吵架。

## 12. 商业价值与落地(v0.1 空缺,这是评分项)

### 12.1 目标用户

第一批用户画像非常清晰:**输入杂、项目多、灵感易失的人**。
- 跨学科研究者与博士生
- 独立创作者(音乐、写作、设计)
- 早期创业者与产品经理
- 咨询与投研从业者

这批人的共同点是:已经在用 Obsidian / Notion,已经有笔记资产,并且**已经在为工具付费**,只是现有工具解决不了他们的问题。

### 12.2 竞品与差异

| 产品 | 它做什么 | 它不做什么 |
|---|---|---|
| Obsidian | 存储、双链、图谱 | 不主动、不推理 |
| Notion AI | 单库问答 | 不跨库、不自我碰撞 |
| NotebookLM | 单库深度问答 | 被动、单人格 |
| ChatGPT Memory | 记住偏好 | 无结构、单人格 |
| Mem / Reflect | 自动关联 | 关联是相似度,不是**辩论生成的** |

我们的护城河不在模型,在于:**用户对新连接的持续反馈,训练出一个"这个用户认为什么算好想法"的偏好模型。** 用得越久越准,且不可迁移。

### 12.3 商业模式

1. **开源核心 + 本地免费**:引擎与副脑格式开源,本地跑自带 key 完全免费。这是获取种子用户的方式,也符合本次比赛的开源承诺
2. **云端订阅**:托管辩论、跨设备同步、更强模型,按月订阅
3. **团队版**:成员的副脑可选择性开放,团队圆桌。这是 v0.1 vision 里"用户与用户之间的副脑交流"的商业化形态,也是收入天花板最高的一块
4. **企业知识库版**:把部门的文档拆成副脑,做立项前的跨部门碰撞

### 12.4 落地路径

```
个人开源工具(获取种子用户,建立副脑格式标准)
  → 云端订阅(变现)
  → 团队版(网络效应开始)
  → 企业版(收入)
```

关键的战略资产是**副脑格式本身**。如果 `brain/` 目录规范能像 Obsidian 的 markdown vault 一样成为事实标准,后面的一切都好做。因此本次开源要把格式规范单独写成文档。

## 13. 合规与伦理(评分项,不能省)

个人知识库是极度敏感的数据,这一节必须在 demo 里花 20 秒讲。

1. **本地优先**:副脑原文存在用户本地文件系统,产品可完全离线运行(自带本地模型时)
2. **最小上传**:云端模式下只传检索出的片段,不传整库
3. **不训练**:明确承诺不将用户数据用于模型训练
4. **全链路溯源**:每条洞察都能点回原始笔记,杜绝"AI 编了一个看起来很聪明的联系"
5. **可删除**:删除副脑即删除目录,无残留
6. **人格声明**:副脑 agent 是知识库的代理,不是用户本人的数字分身。界面上不使用"这是你"的表述,避免用户产生错误的人格投射。这一点在 v0.1 的"用户彻底电子化"表述里有风险,建议对外话术改成"知识的多视角代理",不要说"复制用户"

## 15. 风险与已知不足(自曝,比被评委问出来好)

- 洞察质量高度依赖副脑语料的质量与密度,语料稀疏时容易产出空泛的类比
- 早停阈值目前是人工设定,缺乏自动校准
- 尚未评估辩论产出的洞察相对于"直接问一个大模型"的增益有多大,这是我们最应该在下一阶段做的对照实验
- 多厂商混编在 demo 层面很好看,但差异化收益尚未量化
