# MuseV2

**一句话**：和复旦大学自然语言处理实验室一起，从零搭一个可控的文本生成音乐大模型。

- **时间**：进行中
- **合作方**：[复旦大学自然语言处理实验室](https://nlp.fudan.edu.cn/main.htm)
- **性质**：开源音乐生成模型
- **身份**：**四名初始成员之一**，主导 prompt 数据集生成器的设计（MIT SOI 草稿里的表述：one of the four initial members, lead the design of the structured prompt dataset generator）

## 工作一：结构化 prompt 数据集生成器

一个**确定性的级联 / DAG 采样器**，覆盖 **17 个曲风大类 / 99 个子风格**，生成结构化的歌曲规格，各字段覆盖均衡且彼此条件依赖。设计细节（SOI 里写的）：每个字段从 family profile **层级继承**，经 composable traits 和三条**隐含音乐轴**（aggression、density、acousticness）组合；在 DAG 格式下生成从锚点和逻辑推出，**天然避免 tag 冲突**。

它解决的原始痛点：旧做法是从描述符池随机抽、出现音乐性冲突再补一条消解规则，规则永远补不完。你把它改成从结构生成，冲突根本不会出现。作为制作人你还亲手写了各 genre 的基础配置（每种曲风该听起来什么样），这是「producer 和 researcher 缺一不可」的实例。

## 工作二：歌词结构化（[phone] 至 08-13）

**目标**：为 MuseV2 音频语料补充歌词的段落结构信息，产出 `[Verse1] xxx [Chorus] xxx` 格式。

### 方案演进

**最初计划**：爬 Shazam / Musixmatch，按文件 basename 查歌词结构。

**第一次否定（后被证明判断错了）**：调研后认为 Musixmatch / Shazam 只提供纯歌词文本、没有段落标记，因此建议改走音频侧推断，据此设计了 SongFormer + CTC 强制对齐 + 归并的三段式流水线。

**纠错**：师哥后来指出 Shazam 上确实能看到结构。复查确认：**Musixmatch 官方博客写明他们让 curators 人工标注结构**（intro / verse / pre-chorus / chorus / hook / bridge / outro），2021 年就有数十万首；Shazam 的歌词源就是 Musixmatch。数据一直存在，只是在 **Enterprise 付费层**，免费和 Scale 层拿不到。**最初的判断是错的，而且这个错误直接导致方案改道。**

**Genius 调研结论**：官方 API 不返回歌词正文（lyricsgenius 自己的文档承认是爬网页且违反 ToS）；Genius v. Google 案（2020 一审、2022 二巡维持）中 Genius 败诉，理由是主张被版权法优先适用，歌词版权属于出版商而非 Genius。段落标记是社区自发标注、格式不统一。**结论：适合做小规模验证集，不适合当百万级主力数据源。**

其他关键发现：

- **14.34%（151,147 首）是 Live / DJ 串烧 / 卡拉OK翻唱厂牌 / 伴奏纯音乐**，任何歌词库都不会有

### 最终流水线

```
音频 ──> SongFormer ────> 段落 + 时间戳
                              │
ASR 文本 ─> CTC 强制对齐 ──> 歌词行 + 时间戳
                              │
                    按时间重叠归并 ──> [Verse1][lyrics:xxx]
```

**分工要点**：SongFormer 自带时间戳；CTC 只做一件事，给**已有的**歌词文本补时间轴（qwen3-omni 的 ASR 是纯文本无时间戳）。「强制」意味着它必须用给定文本，一个字不能改，所以文本错了对齐必然错，调参没用。

**如果 ASR 当初就带时间戳（如 Whisper segments），CTC 这一步整个可以省掉。**

### 质检发现（10 首抽样）

人工听感 + 自动检查（19 类规则）交叉验证：

- **对齐塌陷**：找不到锚点时把一句话摊到整段。最极端一行 131 秒只有 23 个字（正常中位数 2.3 秒）。02 的 #24 那行标 31.9 秒，其中 27.4 秒压在纯器乐段上
- **SongFormer 网格化退化**：01/03 段落时长变异系数仅 0.19、中位数恒定 13.7 秒，像固定窗口而非音乐结构
- **边界误差**：08 的副歌标在 2:01.6，实听 2:09 才进，**差 7.5 秒**。SongFormer 论文报 0.5 秒容差下命中率 65-70%，这个偏差远超预期，且纯靠耳朵发现，自动检查无 ground truth 做不到

**质检中犯的三次误报，全靠人耳纠正：**

1. 把 04/07 的副歌重复判成 ASR 退化：实际重复散布全曲 69% 跨度、7 次落在 chorus 上，是正常流行歌
2. 把 06 的副歌低相似度（0.15）判成异常：Onyx 是 hardcore hip-hop，副歌每次词不同是流派常态
3. 把 09 判成对齐失败：那首基本是纯音乐，verse/chorus 标签描述的是**音乐结构而非人声有无**

**共同点：把流行歌的规律当成了普适规则。**

### 全量合并结果

数据：`ctc_merge` 3.5G + `songformer_info` 2.3G + `lyrics_merged` 2.5G + suno 两个文件，共 8.7G。

| | 数量 |
|---|---:|
| union | 2,116,022 |
| ctc ∩ songformer | 1,265,696（占 ctc 的 **99.98%**，basename 匹配很干净） |
| 最终输出 | **1,712,433 条**，已上传 GreenerPat/trans |

- `matched` 1,265,144，格式 `[Intro][Verse1][lyrics:xxx][Chorus1][lyrics:xxx]`
- `unmatched` 330,900，格式 `[lyrics:xxx]`
- `suno` 116,373，自带结构，时间戳剥离后归一化
- 剔除 519,962 条无歌词的空记录

**段落数分布（matched）**：峰值 8 段占 18.1%，7 至 10 段占 60%，3 段及以下仅 7.1%。**全量质量明显好于 10 首抽样给的印象。**

格式校验 90 条样本全过：无残留时间戳、括号配对、能完整正则还原回 (tag, lyrics) 对。

### 性能教训（重要）

**同一份合并逻辑，两种 I/O 策略差 25 倍。**

| 方案 | 原理 | 实测 |
|---|---|---|
| 偏移量索引 | 记录每首歌的字节位置，按需 seek | ETA **400+ 分钟** |
| 分桶 | 顺序扫描 + 按哈希分 16 桶 + 逐桶合并 | **14 分钟** |

**根因**：Seagate 是 USB 机械盘，实测**顺序读 107 MB/s、随机读 13 ms/次**，差两个数量级。索引方案让 200 万首歌 × 3 个文件 = 600 万次磁头寻道（约 21 小时）；分桶方案总共 26GB 顺序 I/O（约 4 分钟）。

**失误**：只优化了内存（8.7G 塞不进 RAM），没意识到把瓶颈挪到了磁盘寻道上。应该一开始就问「盘是机械还是固态」，或者干脆默认走顺序方案，因为**顺序读在两种盘上都快，是严格更安全的默认选择**。另外初版 `read_at` 每次重新 `open()` 文件是纯粹的低级失误，600 万次开关文件的开销与盘类型无关。

**方法论**：性能问题不要靠估计，靠测。一条 10 秒的随机读测试和一条顺序读测试就能定位瓶颈，比任何推理都可靠。

### 遗留事项

- **Musixmatch Enterprise 值得谈**：人工标注质量高于模型推断、标签统一、允许缓存（建数据集的硬需求）。但需注意他们 2025 年 10 月与索尼 / UMPG / Warner Chappell 的 AI 授权**明确限定 non-generative**，生成式用途可能不在覆盖范围，第一封邮件就该说清用途
- **SongFormer 边界误差需量化**：建议人工标 20 至 30 首 ground truth，测 0.5s / 3s 两档容差下的命中率。这个数决定段落时间戳能否直接用于切片
- **90,573 条 FEW_SECTIONS + 74,808 条 ONE_HUGE_SECTION**：格式合法但结构信息稀薄，下游可按 `n_sections` 字段过滤
- **ACE-Step / acestep-transcriber**（MIT、Qwen2.5-Omni）音频直出带段落标记的歌词，ACE-Step 1.5 用它标注过 2700 万首，值得与 SongFormer 交叉验证，两边不一致的自动标低置信度，等于白捡一个质检信号

## 能拿来说的素材

- 「17 个曲风大类 / 99 个子风格的确定性级联采样器，字段覆盖均衡且条件依赖」这一句可以直接用，具体到别人复述不了
- **百万级数据工程的完整交付**：170 万条结构化歌词，从 168 万音频文件的语料摸底到三段式流水线到全量合并，每一步都有数字
- **25 倍的性能教训**是极好的面试素材：同一份逻辑，偏移量索引 400+ 分钟对分桶 14 分钟，根因是 USB 机械盘顺序读 107 MB/s 而随机读 13 ms/次。结论可迁移：**顺序读在两种盘上都快，是严格更安全的默认选择**；以及性能问题靠测不靠估
- **两次公开承认判断错误**，这在面试里比任何正确都值钱：一是 Musixmatch 的结构数据其实存在（只在 Enterprise 层），错误判断直接导致方案改道；二是质检时三次误报全靠人耳纠正，共同点是「把流行歌的规律当成了普适规则」（hardcore hip-hop 的副歌本来就每次词不同）
- **语料摸底本身就是研究**：中日韩文占 32.2%、14.34% 是 Live / DJ 串烧 / 伴奏（任何歌词库都不会有）、stage4-7 的 QQ mid 100% 覆盖可当精确主键。这类「先搞清楚数据长什么样」的功夫和 [[本科荣誉论文 AI音乐检测]] 里的去混淆是同一种直觉
- 这条经历和 [[本科荣誉论文 AI音乐检测]] 是同一个问题的两面：一边造，一边检测。这个对照在 SOP 里很有说服力，**待你确认是否要这么讲**
